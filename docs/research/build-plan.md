# Build the scheduler, rent the isolation

Build this as a self-hostable, Apache-licensed sandbox scheduler whose product is the pool, policy and streaming layer, with the isolation engine as a per-pool setting: hardened rootless Podman with crun first, gVisor (`runsc`) as the no-KVM hardened tier, and Firecracker as a separate backend where `/dev/kvm` exists. The idea as written has two problems the research makes plain. First, rootless containers share the host kernel, and 2026 produced a run of container-escape kernel bugs, at least two of them in CISA's exploited-vulnerabilities catalogue, several of which no seccomp profile compatible with "run arbitrary Python and Bash" can close; a product headlined "rootless Podman" would state the weakest isolation tier in a commercial field that has converged on microVMs and gVisor. Second, the named customers (Lovable, E2B, Cursor, Replit, Cognition) are reference architectures rather than prospects: they run their own VM fleets, buy from a $4.65B vendor, or are direct competitors. What is open is narrower and real: no maintained open-source project combines a warm pool with rootless Podman, the most-starred self-hostable container sandbox (Daytona) was archived in mid-2026, and the remaining self-host routes need Kubernetes, Nomad plus Terraform, or KVM. The recommended build is a Go control plane and per-host agent driving Podman over its REST socket, pre-created idle sandboxes claimed by an atomic Postgres pop and destroyed after one tenant session, cgroup v2 limits verified at start-up, default-deny networking with a forced allowlist proxy, and an in-sandbox agent that owns PTYs and streams over HTTP and WebSocket behind an E2B-shaped SDK. The most decision-relevant numbers (rootless Podman start latency, gVisor overhead on Python, per-host density, Firecracker snapshot-restore time) are not published anywhere with methodology, so the first milestone is a benchmark spike, not a feature.

## The hosted market is closed to a new entrant, but self-hosting is underserved

### Fifteen funded vendors have converged on microVMs and on price

The hosted category has more than fifteen funded providers and has converged on Firecracker, Cloud Hypervisor, custom KVM or gVisor as the boundary. E2B charges **$0.000014 per vCPU-second (about $0.05 per vCPU-hour) and about $0.016 per GiB-hour**, with a $150/month Pro tier and BYOC reserved for an Enterprise plan with a **$3,000/month minimum** ([E2B pricing](https://e2b.dev/pricing)), available on AWS and GCP only ([E2B BYOC docs](https://e2b.dev/docs/byoc)). A vendor-authored fifteen-provider comparison shows Daytona publishing identical rates and several providers undercutting them, and identifies exactly one commercial product using a hardened container as its boundary ([Upstash comparison, 17 Sep 2026, vendor](https://upstash.com/blog/ai-agent-sandbox-providers-compared-2026)); those per-vendor figures come from a single vendor table and need re-verification before reuse. Capital is concentrated: Modal raised $355M at a $4.65B valuation in May 2026 ([bex.co, 11 Sep 2026](https://bex.co/blog/2026/09/11/ai-sandbox-funding-modal-daytona-e2b)), while Blaxel went to Baseten ([The Next Web](https://thenextweb.com/news/baseten-acquires-blaxel-ai-agent-sandboxes)), Koyeb to Mistral ([InfoWorld](https://www.infoworld.com/article/4133757/mistral-ai-deepens-compute-ambitions-with-koyeb-acquisition.html)) and CodeSandbox to Together AI ([Together AI](https://www.together.ai/blog/codesandbox-acquisition-together-code-interpreter)). The hosted layer is consolidating into platforms that bundle sandboxes with inference or hosting. A small team should not enter as a hosted cloud, and no credible sandbox-specific market-size figure exists in free sources.

Vendor cold-start claims are not a reliable target either. A secondary roundup of third-party tests put E2B at about 0.5 s end to end against a 150 ms claim and Daytona at about 0.75 s against a sub-90 ms claim ([bex.co, 25 Sep 2026](https://bex.co/blog/2026/09/25/four-companies-one-sandbox-market-agent-code-execution)). The practical bar for "fast" is therefore a few hundred milliseconds of honest, reproducible time-to-interactive, not double-digit milliseconds.

### The named targets will not buy this, but their customers might

Lovable runs every session on Modal, reports up to 20,000 concurrent sandboxes, and left its previous provider over scalability and vendor risk ([Modal Lovable case study, vendor](https://modal.com/blog/lovable-case-study)). Cursor runs one Firecracker-based microVM per cloud agent in a separate AWS account ([Cursor cloud agent security docs](https://cursor.com/docs/cloud-agent/security)). Devin sessions each run in their own virtual machine ([Devin enterprise deployment docs](https://docs.devin.ai/enterprise/deployment/overview)). E2B is itself a Firecracker sandbox vendor with an Apache-2.0 runtime ([e2b-dev/runtime](https://github.com/e2b-dev/runtime)). No primary source names Replit's isolation runtime, and nothing public was found on Codegen. A rootless-container scheduler from a small team fails both the isolation bar and the vendor-risk bar of every company on the list.

The useful signal from those companies is indirect. Cursor's Self-Hosted Machines let enterprise customers supply the machine where commands run ([Vercel changelog](https://vercel.com/changelog/run-cursor-cloud-agents-vercel-sandbox)), and on 21 July 2026 Cognition opened Devin Outposts, which moves execution onto customer-controlled infrastructure ([Runtimewire](https://runtimewire.com/article/devin-multi-vm-cloud-agents-modal-outposts)). That creates a new buyer: the platform or security engineer who must run agent execution inside their own network on whatever infrastructure they already have. Whether those two protocols accept arbitrary third-party workers was not verified and should be checked before building an adapter.

### The open-source gap is "no Kubernetes required", not "warm pool"

The warm-pool pattern already exists upstream for Kubernetes: kubernetes-sigs/agent-sandbox ships `SandboxWarmPool` and `SandboxClaim` resources with gVisor or Kata isolation ([agent-sandbox docs](https://agent-sandbox.sigs.k8s.io/docs/getting_started/overview/)). Anyone already on Kubernetes will default to it. Self-hosting E2B requires Packer, Terraform and Nomad on GCP or AWS ([Northflank blog, vendor](https://northflank.com/blog/self-hostable-alternatives-to-e2b-for-ai-agents)), and microsandbox requires KVM on Linux ([microsandbox SELF_HOSTING, mirror](https://glama.ai/mcp/servers/@microsandbox/microsandbox/blob/ba02ae334e319faefd8c18dde34bce9822ab3df5/SELF_HOSTING.md)). Daytona's 71,593-star repository is archived, with a README stating that core development moved to a private codebase as of June 2026 ([daytonaio/daytona](https://github.com/daytonaio/daytona)). A search for rootless-Podman agent sandboxes returned only single-user wrapper scripts with no pool or scheduler; absence of search results is not proof that none exists inside companies.

Practitioner complaints line up with what a self-hosted container pool does well. In one Hacker News thread users asked for rootless Podman, for sandboxes that do not live in the cloud, for an outbound firewall because network access is open by default, and complained that ten idle sandbox VMs cost 5 GB of RAM ([HN: Docker Sandboxes](https://news.ycombinator.com/item?id=49239751)). A Fly Sprites user reported over $200 of RAM charges against about $15 of CPU from idle sandboxes ([Fly community forum](https://community.fly.io/t/my-sprites-bill-ended-up-much-larger-than-i-expected/28416)). The same thread also contains the objection the product must answer: plain containers "are not enough isolation".

The positioning that follows is operational, not engine-led: one binary, one Linux box, no root daemon, no Kubernetes, no `/dev/kvm` needed, default-deny egress, warm starts, and an honest statement of which threat model each isolation tier covers. "Rootless" is the more durable message than "no KVM", because AWS enabled nested virtualization on ordinary C8i, M8i and R8i instances in February 2026 ([AWS What's New](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-ec2-nested-virtualization-on-virtual)), which erodes the no-KVM argument on hyperscalers. Realistic early adopters are small agent startups below BYOC minimums, platform teams piloting internal coding agents, evaluation and reinforcement-learning harness operators, CI-style and education workloads, and enterprises needing an execution worker for Outposts-style integrations. This adopter list is inferred from public behaviour; no customer interviews or willingness-to-pay data back it.

## Isolation is a ladder: rootless Podman is the first rung, not the boundary

### What rootless buys, and what the 2026 kernel record takes away

Rootless Podman removes the root daemon and blunts runtime bugs. For the November 2025 runc trio, the advisory lists user namespaces with host root unmapped and non-root-in-container as mitigations ([oss-security 2025-11-05](https://www.openwall.com/lists/oss-security/2025/11/05/3)), and CVE-2025-52881 is described as "entirely mitigated with rootless containers" ([Docker Scout](https://scout.docker.com/v/CVE-2025-52881)). It does nothing for kernel bugs, because untrusted code in a container "calls the host kernel directly" ([Agache et al., NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)). Worse, the user namespaces that make rootless possible widen the reachable kernel surface: one vendor probe reached 8 of 40 tested kernel operations without user namespaces and 27 with them ([Edera, vendor](https://edera.dev/stories/user-namespaces-are-not-a-security-boundary)).

The 2026 record is the decisive fact. CVE-2026-53362 lets "a user with local access inside a container" escape to the host and gain root; Red Hat's workaround is `user.max_user_namespaces=0`, which it warns "breaks rootless Podman" ([Red Hat RHSB-2026-009](https://access.redhat.com/security/vulnerabilities/RHSB-2026-009)). A rootless fleet therefore cannot use the standard emergency mitigation and depends structurally on fast kernel patching. Secondary sources describe further 2026 escapes through AF_ALG, XFRM, RxRPC, AF_UNIX garbage collection and futex priority inheritance ([simeononsecurity, 28 Sep 2026](https://simeononsecurity.com/articles/containers-no-longer-security-boundary-2026/)); apart from CVE-2026-53362 these rest on secondary articles and search digests, and their affected ranges and KEV status must be confirmed against NVD and distro trackers before any security claim is published. The bugs divide into two groups. Those that need namespace creation can be closed by a seccomp profile that blocks `unshare` and `clone` with `CLONE_NEWUSER`. Those reached through AF_UNIX or futex cannot, because CPython cannot run without those syscalls. Only removing the shared kernel closes that second group.

### The hardened baseline, and the honest threat model that goes with it

The first backend should be rootless Podman with crun and every documented hardening control: a dedicated unprivileged host user per pool, `--cap-drop=all`, `--security-opt no-new-privileges`, a custom seccomp profile tighter than the default, `--read-only` with size-capped tmpfs, `--network none` or a filtered proxy path, explicit `--pids-limit`, `--memory` and `--cpus`, default masked paths left intact, AppArmor or SELinux enforcing, and a non-root user inside the container ([podman-run(1)](https://docs.podman.io/en/latest/markdown/podman-run.1.html)). This recipe is a synthesis of documented flags, not a published or tested configuration. Two items need verification on the target host: the two official documents disagree on the default pids limit (2048 versus 1024), and the contents of the installed seccomp profile were not read, so which of `unshare`, `clone3`, `bpf`, `io_uring_*` and AF_ALG it allows is unknown.

This tier is defensible only with a stated threat model: LLM-generated code run on behalf of a trusted or single tenant, where the risks are mistakes and prompt-injection-driven misbehaviour rather than a skilled attacker with a kernel exploit; no secrets or lateral network access in the sandbox; a disposable host that holds nothing else; and kernel updates applied within days. It should not be marketed as hostile multi-tenant isolation.

### gVisor is the cheap second rung; Firecracker is a separate driver

gVisor reimplements the syscall surface in a user-space kernel so that no supported syscall is passed through to the host ([gVisor security model](https://gvisor.dev/docs/architecture_guide/security/)), and its systrap platform runs without virtualization ([gVisor platform guide](https://gvisor.dev/docs/user_guide/platforms/)). It is the only strong-isolation candidate that needs neither KVM nor nested virtualization, and Podman already lists `runsc` among its runtimes ([containers.conf(5)](https://raw.githubusercontent.com/containers/common/main/docs/containers.conf.5.md)). Of gVisor's three rootless methods, only the one where the engine sets up the user namespace is compatible with a scheduler, because `runsc --rootless` does not support `create` ([gVisor rootless guide](https://gvisor.dev/docs/user_guide/rootless/)). The costs are real but unquantified: the official performance guide gives no numbers, its benchmarks ran on a removed platform, and it says overhead is high for many small filesystem operations ([gVisor performance guide](https://gvisor.dev/docs/architecture_guide/performance/)). That implies `pip install`, large import trees and fork-heavy Bash run slower; by how much is the most decision-relevant missing number in the whole research.

Firecracker gives each sandbox its own guest kernel at **125 ms or less to guest init and 5 MiB or less of VMM overhead**, under specific conditions: bare-metal M5D, serial console disabled, a minimal kernel and rootfs ([Firecracker SPECIFICATION.md](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/SPECIFICATION.md)). It is not an OCI runtime for Podman and is not rootless: it needs its own driver for the API socket, jailer, tap devices, rootfs images built from OCI images, a guest agent and a snapshot store, and a small privileged helper to set up networking. Production guidance adds a per-VM UID, default seccomp filters, SMT off, KSM off and swap off ([Firecracker prod-host-setup](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/prod-host-setup.md)). Restoring one snapshot into many sandboxes is the obvious pre-warming move and is exactly what the docs call insecure: unique IDs, cached random numbers and tokens "will still be replicated" across clones ([Firecracker snapshot docs](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/snapshotting/snapshot-support.md)). The same document publishes no restore latency figure.

The other candidates are lower priority. Podman's `krun` runtime puts a container in a libkrun microVM ([crun krun.1.md](https://github.com/containers/crun/blob/main/krun.1.md)), but libkrun's main branch is an unstable 2.0 API ([libkrun mirror](https://upd.dev/containers/libkrun)); treat it as a prototype option. Kata Containers uses a shim API that Podman did not adopt as of the only evidence found, a 2020 mailing-list thread, so choosing Kata means leaving Podman. nsjail and bubblewrap use the same shared-kernel primitives as a container and add no boundary.

| Tier | Boundary | Needs KVM | Rootless | Role in this build |
|---|---|---|---|---|
| Podman + crun, hardened | Shared host kernel | No | Yes | MVP default; single-tenant or semi-trusted code |
| Podman + runsc (gVisor) | User-space kernel | No | Yes, via engine-configured user namespace | Hardened tier on any VM; second backend |
| Podman + krun (libkrun) | KVM microVM | Yes | Reported working, thinly documented | Prototype only |
| Firecracker + jailer | KVM microVM, minimal VMM | Yes | No | Hostile multi-tenant tier; separate driver |

The abstraction is realistic if the backend interface is defined above Podman: create, exec, copy-in, copy-out, snapshot and destroy, plus a capability descriptor per backend (supports snapshot, supports pause, network modes). The main design risk is baking in Podman idioms such as bind mounts and `podman exec` that have no microVM equivalent. An in-sandbox agent that handles exec and file transfer for every backend avoids that, and it is also what the streaming layer needs.

## The pool pops pre-created sandboxes and never returns a used one

### Creation moves off the request path because nothing else is fast enough

crun alone starts a container in about 5.6 ms on a Raspberry Pi 4, and the same engineering work took end-to-end Podman start on that hardware "from almost 2 seconds to under 0.3 seconds" ([Red Hat blog](https://www.redhat.com/en/blog/speed-containers-podman-raspberry-pi)). Everything between those two numbers is Podman's own database and lock I/O, storage mount, network setup and conmon. No published benchmark breaks rootless start latency down by runtime, storage driver and network mode. CRIU is not a way out: Podman checkpoint and restore do not work rootless ([Podman rootless.md](https://github.com/containers/podman/blob/main/rootless.md)). Pre-created idle containers are therefore the primary technique, with an idle running container holding an agent daemon so that assignment is one RPC.

The known start-time levers are native overlayfs over fuse-overlayfs, `--network=none`, a transient store on tmpfs and `--log-driver=none` ([Podman performance tutorial](https://github.com/containers/podman/blob/main/docs/tutorials/performance.md)). One documented exception creates a direct conflict between isolation and speed. With native overlayfs and a UID mapping not previously used with that image, container creation is slower than with fuse-overlayfs, and `--userns auto` is hit hardest because the mapping can change on every run. Yet `--userns=auto` is what gives each sandbox a distinct UID range, so that an escape from one does not land as the owner of another's files. Subordinate-ID arithmetic compounds this: the default allocation is 65,536 IDs per user ([Red Hat rootless Podman](https://www.redhat.com/sysadmin/rootless-podman)), which is one full-width range. The team must decide between per-sandbox ranges (with a much larger root-assigned allocation), a fixed mapping per pool, or several host users each with their own Podman service, and must benchmark create time for each before choosing.

### Size with Little's law, refill immediately, pool per template

The only published sizing rule is Lambda's: pool size is creation rate times creation latency, so "at 125ms creation time, one pooled MicroVM is required for every 8 creations per second" ([Agache et al., NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)). Add a burst reserve, because a drained pool falls off a cliff: in the Kubernetes agent-sandbox tests a burst-tuned configuration served about 57 ms p50 for roughly ten seconds and then about 1.4 s once the pool emptied, and the project recommends a refill rate at least equal to the claim rate with zero replenish delay ([agent-sandbox performance-tuning.md](https://raw.githubusercontent.com/kubernetes-sigs/agent-sandbox/main/docs/performance-tuning.md)). Pools should be per template (image, resource shape, network profile), and a claim must not be able to mutate the template; Tensorlake's pools work exactly this way and replace each claimed instance one for one ([Tensorlake docs](https://docs.tensorlake.ai/sandboxes/pools)). Anything a claim varies, such as environment, tenant identity or files, is injected after creation through the in-sandbox agent.

### One-way lifecycle: warm, assigned, running, destroyed

No surveyed production system resets an instance in place and hands it to another tenant. A Lambda slot serves a single function and is recycled after at most 12 hours ([Agache et al., NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)). The recommended state machine is `CREATING → WARM → ASSIGNED → RUNNING → (PAUSED) → RECYCLING → DESTROYED`, with no edge from `RUNNING` back to `WARM`. An in-place reset would have to clear the writable layer, every tmpfs, all processes, cgroup counters, network state and kernel-held IPC objects, and one missed item is a cross-tenant leak; destroy-and-recreate costs one background create per assignment instead. This is a first-principles design choice supported by the absence of counter-examples, not by measured failure data. Every transient state needs a deadline and an owner, as Fly documents for machines stuck in transient states ([Fly docs](https://docs.fly.io/machines/machine-states)). Each sandbox carries three timers (idle timeout, maximum lifetime, warm-age TTL so pooled instances do not outlive image patches) and a generation token so a late release cannot act on a reassigned ID, the mechanism E2B uses with its `execution_id` guard ([E2B ARCHITECTURE.md](https://raw.githubusercontent.com/e2b-dev/infra/main/docs/ARCHITECTURE.md)).

### A Go agent per host, Postgres as the source of truth, no Kubernetes

Drive Podman through its REST API on the per-user Unix socket using the official Go bindings, which on the current main branch import as `go.podman.io/podman/v6/pkg/bindings` ([bindings README](https://raw.githubusercontent.com/containers/podman/main/pkg/bindings/README.md)). Run `podman system service` with `--time 0`, because by default it exits after five seconds of inactivity, and treat socket access as code execution as the owning user ([podman-system-service(1)](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html)). Quadlet suits the long-lived pieces (the agent, the Podman service, image pre-pull) but not thousands of short-lived uniquely named sandboxes.

E2B's open-source design is the reference for the control plane: a central API "decides where a sandbox runs and tracks that it runs", a per-node orchestrator "owns how it runs", placement is best-of-K over a load score with retry on refusal, and per-team budgets return HTTP 429 with `Retry-After` ([E2B ARCHITECTURE.md](https://raw.githubusercontent.com/e2b-dev/infra/main/docs/ARCHITECTURE.md)). E2B splits state across Postgres, Redis and ClickHouse; the smallest correct starting point is Postgres alone, with the claim implemented as a single `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED)` statement. That avoids the optimistic-concurrency retry storms agent-sandbox measured, 5,447 HTTP 409 conflicts in one test ([agent-sandbox performance-tuning.md](https://raw.githubusercontent.com/kubernetes-sigs/agent-sandbox/main/docs/performance-tuning.md)). Move the warm free-list to Redis only when claim throughput demands it. Correctness comes from a level-triggered reconciliation loop: each container is labelled with sandbox ID, generation and agent epoch, and after a crash the host agent lists containers by label, destroys orphans, and never re-adopts a container as warm unless its row agrees.

Kubernetes plus agent-sandbox is the sensible alternative only for teams that drop the rootless-Podman requirement and already run Kubernetes; its warm claims reach about 300 per second at p90 of 200 ms or less, but its cold path on GKE was 41 to 51 seconds at p50. Multi-host scheduling is a second milestone. When it arrives, overcommit CPU rather than memory and cap sandboxes per tenant per host, following Lambda's argument that oversubscription is safe only across uncorrelated workloads.

## Limits and egress are enforced from outside the sandbox, or not at all

### cgroup v2 delegation is a start-up check, not an assumption

Rootless Podman supports no resource limits on cgroup v1 hosts ([Podman rootless.md](https://github.com/containers/podman/blob/main/rootless.md)). On cgroup v2, limits work only for controllers systemd delegates to the user session: upstream systemd ships `Delegate=pids memory cpu` ([systemd user@.service.in](https://raw.githubusercontent.com/systemd/systemd/main/units/user@.service.in)), so `cpuset` and `io` need a root-installed drop-in, and Podman's own troubleshooting guide shows an older configuration lacking `cpu` ([Podman troubleshooting.md](https://github.com/containers/podman/blob/main/troubleshooting.md)). Per-distribution defaults were not confirmed. The host agent should read its `cgroup.controllers` at start-up and refuse to run if `cpu`, `memory` or `pids` is missing, since Podman otherwise fails per container with "the requested cgroup controller `cpu` is not available". It also needs lingering enabled and a real systemd login session.

Set `--cpus`, `--memory`, `--memory-swap` equal to `--memory` (the swap default is double the memory value), and `--pids-limit` on every sandbox ([podman-run(1)](https://docs.podman.io/en/latest/markdown/podman-run.1.html)). `pids.max` is the fork-bomb control; `nproc` ulimits apply per user rather than per container and must not be used. Lower `nofile` from its 1,048,576 default. Use `--cgroup-conf` to set `memory.high` below the hard limit for throttling before a kill, and export `memory.events` `oom_kill` and `cpu.stat` throttling counters per sandbox so every termination has an observable reason ([Kernel cgroup v2 doc](https://docs.kernel.org/admin-guide/cgroup-v2.html)). That answers the "silent kill" complaint directly.

Disk is the weakest rootless control. Per-container writable-layer quotas require an XFS filesystem mounted with `pquota` ([containers-storage.conf(5)](https://github.com/containers/storage/blob/main/docs/containers-storage.conf.5.md)), a root-level host setup whose rootless behaviour was not confirmed. The portable design is a read-only rootfs with size-capped tmpfs mounts for the work directory and `/tmp`. tmpfs is charged to the memory cgroup, so the tmpfs cap must be budgeted inside the memory limit, and filling it can trigger the OOM killer instead of a disk-full error. I/O throttling needs the `io` controller, a real block device and a filesystem with cgroup writeback support, so expect it to be approximate.

For wall-clock limits, layer four mechanisms: a per-exec deadline in the scheduler, Podman's `--timeout` enforced by conmon, a scheduler-side `podman rm -f`, and as a last resort writing `1` to the container cgroup's `cgroup.kill`, which SIGKILLs the whole subtree and handles concurrent forks ([Kernel cgroup v2 doc](https://docs.kernel.org/admin-guide/cgroup-v2.html)). Go straight to SIGKILL for untrusted code. Whether a rootless user can write `cgroup.kill` for a Podman-created scope in every configuration needs a test.

### Default-deny with a forced proxy; pasta alone is not an egress lock

`--network=none` creates a namespace with no interfaces and is the only mode that is deny-by-default with no moving parts. pasta, the default rootless network tool and per the Podman performance guide the only one since Podman 6.0.0, copies host addresses and routes into the namespace, and its man page has no option that restricts outbound destinations ([passt(1)](https://passt.top/builds/latest/web/passt.1.html)). A sandbox on plain pasta can reach the host's LAN, private peers and the cloud metadata address. Setting `HTTP_PROXY` on top of pasta is advisory, not a control.

Two rootless topologies turn the proxy into a routing fact. The tightest is `--network=none` with a host-side proxy reached over a bind-mounted Unix socket, the pattern Anthropic's sandbox-runtime uses with bubblewrap ([sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)). The more convenient is a Podman `--internal` bridge, which adds no default route and disables forwarding ([podman-network-create(1)](https://docs.podman.io/en/latest/markdown/podman-network-create.1.html)), shared only with an egress-proxy container that also has an outbound network. Both need a hands-on test, including attempting `nft flush ruleset` from inside the sandbox with and without a nested user namespace, because no primary source confirms the tamper-resistance argument.

The proxy must allowlist by hostname, resolve the name once itself, reject the result if it falls in a denied range, and then connect to that exact IP; that sequence is the DNS-rebinding defence. Stripe's Smokescreen does hostname ACLs per client role and requires resolved IPs to be publicly routable ([stripe/smokescreen](https://github.com/stripe/smokescreen)). sandbox-runtime's default denied set covers loopback, link-local, the cloud metadata addresses `169.254.169.254`, `100.100.100.200` and `168.63.129.16`, and the host's own interface addresses, but not RFC 1918 space, which must be added. The sandbox should have no resolver of its own, since any recursive resolver is an exfiltration channel through query labels. Every vendor documents the limit of this design: filtering on the client-supplied hostname or SNI without terminating TLS is bypassable by domain fronting ([Modal sandbox networking](https://modal.com/docs/guide/sandbox-networking), [Vercel Sandbox firewall](https://vercel.com/docs/vercel-sandbox/concepts/firewall)). The MVP should state that limit and recommend narrow single-purpose hostnames; TLS termination with a per-sandbox CA is a later feature.

The API should follow market convention with three modes (none, allowlist, full), domain and CIDR lists with deny winning, and a live policy update so "install dependencies, then lock down" is one sandbox; E2B, Modal and Vercel all offer runtime updates. Because per-sandbox policy lives in the proxy's ACL and not in the network namespace, it can change live without violating the rule that claims do not mutate templates. Default to none, since most commercial products default to allow-all. Credential injection, where the proxy swaps a placeholder for a real secret on allowlisted hosts so "the secrets never enter the sandbox" ([Vercel Sandbox firewall](https://vercel.com/docs/vercel-sandbox/concepts/firewall)), reuses the same proxy and is a strong post-MVP differentiator. On Firecracker the equivalent is a per-VM network namespace with a default-drop forward chain and an explicit metadata drop rule, since Firecracker does no filtering and its reference setup is allow-all ([Firecracker network-setup](https://github.com/firecracker-microvm/firecracker/blob/main/docs/network-setup.md)).

## An in-sandbox agent owns the PTY; the SDK looks like E2B's

### Podman's exec API cannot reattach, so every product ships a daemon

Podman's REST API hijacks the HTTP connection for attach and exec, multiplexes stdout and stderr with an 8-byte frame header when no TTY is allocated, and sends a raw merged stream when one is ([podman register_containers.go](https://raw.githubusercontent.com/containers/podman/main/pkg/api/server/register_containers.go)). Resize is a separate POST, there is no in-band exit code, and exec sessions are removed five minutes after they exit ([podman register_exec.go](https://raw.githubusercontent.com/containers/podman/main/pkg/api/server/register_exec.go)). No documented way to reattach to a running exec session or replay its output was found, so a gateway restart or client drop loses the stream. Hosted products solve this the same way: E2B's `envd` is a Go daemon inside the sandbox whose process service offers `Start`, `Connect`, `List`, `Update`, `SendInput` and `SendSignal`, selected by PID or caller-supplied tag ([envd process.proto](https://raw.githubusercontent.com/e2b-dev/infra/main/packages/envd/spec/process/process.proto)), and Daytona's toolbox exposes PTY sessions whose WebSocket can be closed "without killing the shell" and reattached ([Daytona PTY docs](https://www.daytona.io/docs/en/pty)).

Use the Podman API only for lifecycle, and run a statically linked Go agent as the sandbox's long-lived process for all exec, PTY and file traffic. With `--network=none`, the agent listens on a Unix socket bind-mounted from the host; this is a design recommendation, and its interaction with gVisor needs a spike. Offer two execution modes: pipe mode with separate stdout and stderr for one-shot agent commands, and PTY mode with one merged stream, resize and Ctrl+D for interactive sessions. `creack/pty` is the standard Go PTY library ([pkg.go.dev creack/pty](https://pkg.go.dev/github.com/creack/pty)).

### Two transports and a protocol with exit, flow control and replay designed in

The idea's "WebSocket TTY streaming" is right for the interactive path and wrong as the only transport. E2B streams command output over Connect RPC on plain HTTP with a keepalive every 50 seconds and SDK-side reconnect ([E2B sandbox lifetime FAQ](https://docs.e2b.dev/faq/sandbox-lifetime)); Daytona uses REST plus a WebSocket for PTY; Cloudflare deprecated its WebSocket transport in favour of multiplexed RPC ([Cloudflare Sandbox architecture](https://developers.cloudflare.com/sandbox/concepts/architecture/)). Build a REST control plane, server-streaming HTTP from a protobuf schema for "run and stream output", and WebSocket only for PTY sessions.

For the WebSocket, use binary frames with a one-byte channel prefix aligned with Kubernetes: 0 stdin, 1 stdout, 2 stderr, 3 status, 4 resize ([apimachinery remotecommand constants.go](https://raw.githubusercontent.com/kubernetes/kubernetes/master/staging/src/k8s.io/apimachinery/pkg/util/remotecommand/constants.go)). Kubernetes needed protocol revisions v4 and v5 to add exit codes and a close signal, which argues for an explicit terminal event carrying exit code, signal and reason (exited, killed, timeout, OOM) in version 1. None of the examined protocols provides replay on reconnect or end-to-end flow control. Add a sequence number per stream, a bounded ring buffer in the agent, and a `connect(pid, from_offset)` call that replays or returns a truncation marker. For backpressure, follow the xterm.js guidance of application-level ACKs with high and low watermarks (its example uses 100,000 and 10,000 bytes) so a slow consumer pauses reads from the PTY master and gateway memory stays bounded ([xterm.js flow control guide](https://xtermjs.org/docs/guides/flowcontrol/)). `coder/websocket` supports context cancellation and concurrent writes ([coder/websocket](https://github.com/coder/websocket)).

### Table stakes for the API, and two credential tiers

Across E2B, Daytona, Modal, Vercel, Cloudflare and Runloop the common core is: create from a template with timeout and metadata, foreground command with streamed output and exit code, background command with ID, reconnect and kill, file read and write, list, get and kill, and Python and TypeScript SDKs. Adopt E2B's naming (`Sandbox.create`, `commands.run`, `files.write`, `setTimeout`, `kill`) to minimise friction for agent frameworks; the API-stability and trademark implications of strict compatibility were not researched. Expose three separate timeouts: sandbox lifetime, idle, and per-command. Ship an MCP server as a thin wrapper over the REST API. Preview URLs, snapshots, pause and resume, and a Jupyter-style stateful interpreter are expected in 2026 but belong after the MVP.

Authentication follows an established two-tier pattern: a long-lived project API key on the control plane, and a per-sandbox token returned at create time for direct data-plane calls, as E2B does with its `X-Access-Token` header ([E2B secured access](https://docs.e2b.dev/docs/sandbox/secured-access)). Browser terminals cannot set arbitrary WebSocket headers, so they need a signed URL with an expiring, revocable token, the form Daytona offers ([Daytona preview docs](https://www.daytona.io/docs/en/preview)). Rate-limit per tenant and endpoint class with 429 and `Retry-After`, enforce the concurrent-sandbox quota transactionally at create time, and persist an execution record (command, exit code, termination reason, output byte counts, truncation flag) because Podman will not keep it. Emit lifecycle events as one append-only stream that feeds audit, metering and webhooks.

## The plan: measure first, ship a single-node MVP, then climb the isolation ladder

### Five phases, each with an exit gate

The sequencing below is this report's synthesis; the durations are planning assumptions for a team of one to three engineers, not sourced figures.

|---|---|---|---|
| 0. | 2. | 3. | 4. The MVP is phases 0 through 2: a single-node warm pool with claim, release and recycle-on-release; per-sandbox CPU, memory, pids and disk bounds with hard TTL and idle timeout and explicit termination reasons; default-deny egress with a per-sandbox allowlist; exec, file transfer and streaming TTY; a small REST API with two SDKs; API keys and basic metrics. It explicitly defers memory snapshot and fork, GPUs, multi-region, a hosted cloud, non-Linux guests and browser or desktop images. Monetisation comes later, through support, an enterprise control plane (SSO, audit, multi-node) or a managed control plane with customer-run workers.

### Five risks that could sink it

Isolation credibility is the first. Shared-kernel containers will be rejected for hostile multi-tenant code, and OpenAI's disclosed sandbox escapes in 2026 raised buyer scrutiny ([Fortune, 26 Sep 2026](https://fortune.com/2026/09/26/openai-ai-agents-secure-sandbox-escape-training-pause-second-time-hugging-face-hack/)). The mitigation is the tiered runtime, honest per-tier threat models, and a kernel patch process measured in days. Second, upstream absorption: Alibaba's OpenSandbox, Tencent's CubeSandbox and NVIDIA's OpenShell each reached five-figure star counts within a year, and Podman or agent-sandbox could add the same pool feature. Speed and a narrow, well-benchmarked niche are the only defence. Third, the no-KVM argument weakens as clouds expose nested virtualization, which is why "rootless and no Kubernetes" must carry the message. Fourth, the performance premise is unverified: the positioning assumes warm-claim latency and density are competitive, and nothing published confirms it. Phase 0 exists to find out before code is written. Fifth, monetisation: the buyers who value self-hosting most are the least willing to pay for software, and Daytona's retreat to a private codebase shows how that pressure resolves.

## Conclusion

The research inverts the original pitch. The scarce thing is not a faster or safer sandbox, which well-funded vendors already sell at commodity prices, but a sandbox pool that an ordinary team can run on an ordinary Linux box without root, Kubernetes or a cloud contract, at exactly the moment agent vendors are starting to ask their enterprise customers to supply the execution machine. The engine becomes a configuration choice and the scheduler, policy and streaming layers become the product, which also means the hardest security question is answered by reusing gVisor and Firecracker instead of defending containers.

The plan is also unusually falsifiable. Two weeks of benchmarking will show whether rootless Podman delivers warm claims and density worth publishing, and whether gVisor's overhead on Python workloads is tolerable. If both hold, the project has a defensible niche and a credible upgrade path. If the density or latency numbers disappoint, the correct response is to keep the control plane and move the default tier up the ladder, which the backend abstraction is designed to permit.
